# PIPA 변경분 리뷰

변경된 코드에서 개인정보 후보가 저장·전송·로그·응답 등의 sink에 도달하는 경로와 보호조치를
확인하고, pipa-guard의 활성 규칙과 조항 원문에 대응한 리뷰를 작성한다.

## 원칙

- 리뷰 요청만 받았다면 읽기와 진단만 한다. 코드·설정·PR·이슈를 수정하거나 게시하지 않는다.
- 대상 저장소의 `AGENTS.md`와 하위 작업 지침을 먼저 따른다.
- 규칙 ID·상태·신뢰도는 `rules/rules.json`, 조항 원문은 `rules/articles.md`, 개인정보 후보는
  `rules/pii_items.json`을 단일 출처로 사용한다. 기억으로 규칙이나 조항을 만들지 않는다.
- `status: active`인 규칙만 구현된 판정으로 보고한다. `planned`·`deferred` 규칙 또는 엔진이
  지원하지 않는 구조는 실제 검사 ID를 붙이지 말고 **지원 범위 밖 확인사항**으로 분리한다.
- 차단 판단은 개인정보 후보, 보호 대상 sink 도달, 보호조치 부재가 모두 확인될 때만 한다.
  하나라도 불명확하면 high로 단정하지 않는다.
- `.pipa.json`의 정보주체·저장 위치·전송 경계·출력 목적·접속기록·로컬 저장 정책은 코드 밖의
  필수 판정 입력이다. 설정 누락을 임의의 배포 환경으로 추정하지 않는다.
- Finding의 조항 인용은 원문 그대로 쓴다. 요약은 별도의 해석으로 표시하고 원문 칸에 섞지 않는다.
- 주민등록번호 전체 값과 비밀값을 근거에 싣지 않는다. 엔진의 redacted evidence를 우선 사용하고,
  수동 근거도 값 대신 식별자·호출 구조만 남긴다.
- 회사 코드베이스의 결과를 외부 서비스, 공개 문서, PR 코멘트나 이슈로 전송·게시하지 않는다.
  실제 코드베이스 결과로 재현율·오탐율이나 제품 효과 수치를 만들지 않는다.

## 리뷰 범위 확정

사용자가 지정한 커밋·브랜치·PR·파일 범위가 있으면 그것을 우선한다. 지정이 없으면 현재 작업
트리의 다음 세 범위를 모두 확인한다.

1. staged 변경
2. unstaged 변경
3. untracked 파일

`git diff`만 사용하면 untracked 파일이 빠진다. `git status --short`, `git diff --cached`,
`git diff`를 함께 보고 최종 파일 내용도 읽는다. 삭제 파일은 diff로만 검토하고 엔진 입력에서는
제외한다. 생성물·vendor·빌드 출력은 저장소 지침과 `.pipa.json.exclude`를 따른다.

## 판정 절차

1. `rules/rules.json`, `rules/articles.md`, `rules/pii_items.json`, 대상 프로젝트의 `.pipa.json`을
   읽어 현재 활성 규칙과 판정 맥락을 확정한다.
2. 변경된 Java·Kotlin 최종 파일을 pipa-guard CLI의 `--json`으로 검사한다. 플러그인 루트를 알 수
   있으면 그곳의 `bin/pipa_check.py`를 사용하고, pipa-guard 저장소 자체에서는 저장소의 엔진을
   사용한다.
3. CLI 종료코드를 구분한다: `0`은 high 없음, `1`은 high 존재, `2`는 검사 파일 없음,
   `3`은 엔진 오류다. `3`을 위반으로 해석하지 말고 해당 범위의 판정이 불완전하다고 보고한다.
4. diff를 수동으로 따라 `개인정보 후보 → 값 전파 → sink → 보호조치`를 확인한다. 엔진이 파일
   전체를 검사하므로, 기존 코드의 Finding인지 이번 변경이 만들거나 악화한 Finding인지 구분한다.
5. 엔진 결과마다 실제 변경과의 관련성, 식별자 매칭 강도, sink 연결, 보호조치 부재,
   `.pipa.json` 계약을 대조한다. 근거가 부족한 결과를 high로 재서술하지 않는다.
6. 엔진이 아직 지원하지 않는 프레임워크·파일 밖 호출 그래프·운영 통제는 누락 가능성을 확인하되,
   법적 근거가 확정되지 않은 독립 의무를 만들지 않는다.
7. 저장소 지침이 요구하는 관련 테스트를 실행할 수 있으면 실행한다. 테스트 실패와 개인정보
   Finding은 서로 다른 결과로 보고한다.

## 결과 형식

가장 중요한 Finding부터 `high → medium/low → 지원 범위 밖 확인사항` 순으로 쓴다. 각 Finding에는
다음을 포함한다.

- 신뢰도와 실제 `규칙/check` ID
- 파일과 줄
- 개인정보 후보, sink, 보호조치 부재를 보여 주는 짧고 가린 근거
- 적용 조항 번호와 `rules/articles.md`의 원문
- 이번 변경과의 관계
- 조항을 충족시키는 구체적인 수정 방향

그 뒤 변경 경로 전체를 다음 대응표로 요약한다.

| 변경 경로 | 개인정보 후보 | sink | 확인된 보호조치·정책 | 규칙·조항 | 판정 |
|---|---|---|---|---|---|

개인정보와 무관한 변경도 누락하지 말고 `대상 없음`으로 표시하거나, 행이 지나치게 많으면 파일 수와
제외 기준을 밝힌 뒤 묶는다. Finding이 없으면 “검출 없음”이라고만 끝내지 말고 검사한 범위,
적용한 설정, 엔진의 현재 지원 경계, 실행한 검증을 함께 적는다. 검출 없음은 전체 법령 준수 보증이
아니다.
