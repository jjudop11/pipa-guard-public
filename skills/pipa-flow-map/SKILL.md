# 개인정보 흐름도

코드에서 확인되는 개인정보 후보의 시작점, 변환, sink와 운영 경계를 연결해 검토 가능한 흐름도
초안을 만든다. 이 결과는 코드 기반 검토 자료이며 전체 개인정보 처리 현황이나 인증 적합성을
보증하지 않는다.

## 원칙

- 흐름도 요청만 받았다면 읽기와 분석만 한다. 사용자가 경로를 지정했을 때만 로컬 파일로 저장하고,
  코드·설정·외부 시스템은 수정하지 않는다.
- 대상 저장소의 `AGENTS.md`와 하위 작업 지침을 먼저 따른다.
- 규칙 ID·상태·신뢰도는 pipa-guard 플러그인 루트의 `rules/rules.json`, 조항 원문은
  `rules/articles.md`, 개인정보 후보는 `rules/pii_items.json`을 실행 시점의 단일 출처로
  사용한다. 스킬에 적힌 예시를 현재 규칙으로 간주하지 않는다.
- `.pipa.json`의 `subjectType`, `storageZone`, `riskAssessment`, `inboundTransport`,
  `outputPolicies`, `accessLogPolicies`, `localStoragePolicies`는 코드 사실이 아니라 프로젝트가
  선언한 운영 맥락이다. 값과 `evidence`를 함께 표시하고 실제 환경으로 단정하지 않는다.
- 엔진 Finding은 흐름의 주석이지 흐름 전체의 존재 증명이나 준수 보증이 아니다. Finding이 없어도
  지원하지 않는 프레임워크, 파일 밖 호출, 운영 통제와 설정 공백을 따로 남긴다.
- 주민등록번호 전체 값, 비밀번호, 토큰, 키와 실제 개인정보 값은 읽을 필요가 있는 최소 범위를
  넘겨 복사하지 않는다. 노드와 표에는 항목명·식별자·호출 구조만 쓰고 값은 가린다.
- 회사 코드베이스의 흐름도, 검출 건수, 규칙 분포와 코드 조각을 외부 서비스나 공개 문서·PR·이슈에
  전송하거나 게시하지 않는다. 실제 결과로 재현율·오탐율 또는 제품 효과 수치를 만들지 않는다.

## 범위 확정

사용자가 지정한 저장소·모듈·파일·유스케이스를 우선한다. 지정이 없으면 현재 저장소의 지원되는
Java·Kotlin 소스를 대상으로 삼고, 저장소 지침과 `.pipa.json.exclude`를 따른다. 범위가 너무 커서
한 장에서 관계를 읽기 어렵다면 모듈·유스케이스·신뢰 경계별로 나누고 같은 흐름 ID로 연결한다.

변경분 흐름도를 요청한 경우에는 `git status --short`, staged, unstaged, untracked를 모두 확인하고
최종 파일 내용에서 경로를 추적한다. 삭제된 파일은 diff 근거로만 표시한다. 생성물·vendor·빌드
출력은 저장소 규약에 따라 제외하고, 제외한 범위를 결과에 적는다.

## 증거 수준

모든 연결선에 다음 중 하나를 붙인다. 같은 이름이라는 이유만으로 메서드나 파일을 가로질러 연결하지
않는다.

- **코드 확인**: 같은 메서드의 대입·인자·반환 또는 명시적 호출과 타입·시그니처로 값 이동을 직접
  확인했다.
- **설정 선언**: `.pipa.json`의 선택자와 비어 있지 않은 근거가 경계·목적·저장 위치를 선언한다.
  코드 확인과 별개의 증거다.
- **추론**: DTO 매핑, 프레임워크 주입 또는 파일 밖 호출 때문에 연결 가능성은 높지만 직접 이어지는
  값 이동을 확인하지 못했다. 추론 이유를 쓴다.
- **미확인**: 생산자·소비자·경계 중 필요한 연결을 찾지 못했다. 선을 임의로 잇지 말고 공백으로
  기록한다.

흐름 전체를 하나의 신뢰도 숫자로 뭉개지 않는다. 코드 연결 수준과 운영 경계의 선언 수준을 각각
표시한다. `설정 선언`을 `코드 확인`으로 승격하거나, `추론`·`미확인` 흐름에 high 위반을 새로
붙이지 않는다.

## 추적 절차

1. pipa-guard 플러그인 루트의 `rules/rules.json`, `rules/articles.md`, `rules/pii_items.json`과
   대상 프로젝트의 `.pipa.json`을 읽어 활성 규칙, 후보 사전, 제외 범위와 운영 선언을 확정한다.
2. 컨트롤러 요청 바인딩, 메서드 인자, 메시지·파일·저장소 읽기와 객체 생성을 시작점 후보로 찾는다.
   코드만으로 정보주체, 수집 목적이나 실제 외부 유입을 알 수 없으면 추론 또는 미확인으로 둔다.
3. 대입, 생성자·setter·builder, 메서드 인자·반환을 메서드 안에서 먼저 따라간다. 파일 밖 연결은
   호출 대상과 타입·시그니처 또는 명시적 DTO 매핑이 맞을 때만 잇는다.
4. 암호화·일방향 암호화·마스킹과 단순 인코딩을 구분한다. Base64, URL 인코딩, 직렬화나 이름만
   `encrypt`인 메서드를 보호조치로 단정하지 않는다.
5. 영속 저장, SQL, 파일, 외부 HTTP, 로그, API 응답을 sink 후보로 찾고 실제 개인정보 값이 해당
   인자나 반환값에 도달하는지 확인한다. 메서드 이름만으로 sink를 만들지 않는다.
6. 가능한 범위에 플러그인 루트의 `bin/pipa_check.py`를 `--json`으로 실행해 구조화된 Finding을
   대응한다. 종료코드 `0`은 high 없음, `1`은 high 있음, `2`는 검사 파일 없음, `3`은 엔진
   오류다. `3`이면 해당 범위가 판정되지 않았다고 표시한다.
7. 활성 규칙이 지원하지 않는 프레임워크·동적 디스패치·리플렉션·메시지 브로커·파일 밖 호출 그래프와
   운영상 암호화·접근통제는 `지원 범위 밖/추가 근거 필요`로 남긴다. 존재하지 않는 검사 ID나 법적
   의무를 만들지 않는다.
8. 모든 sink가 시작점까지 연결되었는지, 모든 경계 선언에 코드 위치가 있는지 역방향으로 대조한다.
   끊긴 연결을 삭제해서 그림을 깔끔하게 만들지 않는다.

## 결과 형식

먼저 분석 범위, 제외 범위, 적용한 설정 파일, CLI 결과와 생성일을 짧게 쓴다. 이어서 Mermaid
`flowchart LR`로 흐름도를 만든다.

- 흐름은 `FLW001`처럼 안정적인 ID를 사용한다.
- 노드는 `SRC001`(시작점), `TRN001`(변환), `SNK001`(sink), `BND001`(경계)처럼 역할별 ID를
  사용한다.
- 노드 라벨에는 개인정보 항목 또는 묶음, 컴포넌트·메서드와 역할만 쓴다. 실제 값과 긴 코드 조각은
  넣지 않는다.
- 연결선에는 흐름 ID, 변환과 증거 수준을 짧게 표시한다. 외부·내부, 서버·단말처럼 설정이 선언한
  신뢰 경계는 subgraph 또는 경계 노드로 표현한다.
- 흐름이 많으면 한 장에 우겨 넣지 말고 여러 그림으로 나누되 흐름 ID를 유지한다.

그 뒤 다음 증거표를 붙인다.

| 흐름 ID | 개인정보 항목·매칭 강도 | 시작점 | 변환·보호조치 | sink | 운영 경계·정책 | 코드 증거 | 규칙·Finding |
|---|---|---|---|---|---|---|---|

파일과 줄은 표의 시작점·변환·sink에 넣어 그림을 읽기 쉽게 유지한다. 조항 원문을 싣는다면
`rules/articles.md`에서 그대로 인용하고, 해석은 별도 문장으로 구분한다. 준수로 보이는 흐름,
위반 Finding이 붙은 흐름, 판정 불가 흐름을 서로 다른 상태로 표시한다.

마지막에 다음 공백 표와 한계를 적는다.

| 위치·흐름 ID | 끊긴 연결 또는 미확인 경계 | 필요한 코드·설정·운영 근거 | 영향 |
|---|---|---|---|

Finding이 없더라도 “개인정보 흐름 없음”이라고 쓰지 않는다. 확인한 범위, 발견한 흐름, 지원 범위 밖,
미확인 연결과 설정 공백을 밝혀 독자가 그림의 증거 한계를 알 수 있게 한다.
